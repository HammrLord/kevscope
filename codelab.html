Find a real-time deadline miss on QNX 8.0 in 20 minutes

⏱ 20 minQNX SDP 8.0 + QEMU quick-start imageLevel: beginnerTools: tracelogger · traceprinter · kevscope
Draft codelab for the QNX Global Hackathon. Commands follow the QNX 8.0 documentation; each step is being re-verified on a fresh SDP 8.0 install.
You will
  1. Boot a QNX 8.0 target in QEMU
  2. Build and run a 1 kHz control loop with a misbehaving logger
  3. Capture a kernel trace with tracelogger
  4. Convert it with traceprinter
  5. Let kevscope find the missed deadlines and the thread that caused them
  6. Fix it and prove the fix

1Boot a QNX 8.0 target

Install SDP 8.0 with the free non-commercial licence (myQNX → QNX Software Center), then add the Quick Start Target Image for QEMU. On macOS, use the official Docker build environment (qnx/projects/docker-mac).

source ~/qnx800/qnxsdp-env.sh
mkdir ~/qnx-vm && cd ~/qnx-vm
mkqnximage --arch=x86_64 --run

Tracing needs the instrumented kernel (procnto-smp-instr), which the quick-start images use.

2Build the sample workload

examples/rtloop.c runs a 1 kHz control loop and a same-priority FIFO "logger" that burns 2.5 ms every 200 ms.

git clone https://github.com/HammrLord/kevscope && cd kevscope
qcc -Vgcc_ntox86_64 -o rtloop examples/rtloop.c
scp rtloop root@<target-ip>:/tmp/

3Capture a trace

# on the target
/tmp/rtloop &
tracelogger -n 20 -f /tmp/rtloop.kev
# copy it back to the host
scp root@<target-ip>:/tmp/rtloop.kev .

tracelogger must run as root. -n sets how many buffers to capture.

4Convert to text

traceprinter -f rtloop.kev > rtloop.txt

Multi-gigabyte .kev files can overwhelm GUI viewers. kevscope reads the text stream line by line, so size doesn't matter.

5Analyse with kevscope

node cli/kevscope.mjs rtloop.txt -o report.html
# or stream directly:
traceprinter -f rtloop.kev | node cli/kevscope.mjs - -o report.html

Open report.html, or drop rtloop.txt on the web version. Look at Findings: kevscope reports how many times ctl_loop waited more than 100 µs between READY and RUNNING, the worst wait, and which thread held the CPU (expected: flush). The timeline opens on the worst stall.

6Fix it and prove it

Give the control loop a higher priority than the logger (or pin the logger elsewhere with a runmask), rebuild, and re-capture:

sed -i 's/set_name_prio("ctl_loop", 20)/set_name_prio("ctl_loop", 30)/' examples/rtloop.c
qcc -Vgcc_ntox86_64 -o rtloop examples/rtloop.c   # then repeat steps 3–5

The deadline-miss count should drop to zero and the latency histogram should lose its red tail. That's your before/after evidence.

✓What you learned

  • How FIFO scheduling at equal priority lets a background thread starve a real-time loop
  • How to capture and convert QNX kernel traces
  • How to read scheduling latency (READY→RUNNING), IRQ and kernel-call timing

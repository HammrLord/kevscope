# kevscope

**Find the 900 µs stall hiding in a 2 GB QNX trace.**

kevscope is a host-side trace analyser for QNX 8.0. It streams `traceprinter` output in constant memory and reports:
- which threads missed their scheduling deadlines (READY → RUNNING latency over a budget)
- how late they were, and which thread was holding the CPU when it happened
- interrupt (ISR) and kernel-call timing, including MsgSend round trips

It runs as a CLI or in the browser. Nothing is uploaded.

- **Codelab:** https://hammrlord.github.io/kevscope/codelab.html

Built for the **QNX Global Hackathon 2026**, in the Developer Tooling & Host Tools category.

## Why
- In the QNX Toolkit, `.kev` traces of 1.4 GB or more can crash VS Code (SDP 8.0 known issue Ref# 3001424).
- A 1 kHz control loop has 1,000 µs per cycle, so finding one 900 µs stall by scrolling a timeline is painful.
- kevscope answers the question directly: *who missed the deadline, and who caused it?*

## Build and run
Requirements: Node 18+. There are no dependencies.

```bash
git clone https://github.com/HammrLord/kevscope && cd kevscope
npm test                                   # unit tests

# on the target (QNX 8.0, instrumented kernel):
tracelogger -n 20 -f /tmp/app.kev
# on the host:
traceprinter -f app.kev > app.txt
node cli/kevscope.mjs app.txt -o report.html          # self-contained HTML report
traceprinter -f app.kev | node cli/kevscope.mjs - -o report.html   # or stream directly
node cli/kevscope.mjs app.txt -o report.html --json    # also write report.json
```

Web version: `python3 -m http.server 8000`, then open http://localhost:8000 and drop `app.txt` on the page.

Example workload: `examples/rtloop.c` is a 1 kHz loop plus a same-priority FIFO logger. Build it with `qcc -Vgcc_ntox86_64 -o rtloop examples/rtloop.c`. The [codelab](codelab.html) walks through every step.

## How it works
- `src/analyzer.js` parses traceprinter event lines (`t:`, `CPU:`, `CLASS:EVENT`, key:value pairs) and the indented `pid:`/`name:` lines under `PROCCREATE_NAME` and `THCREATE`.
- It keeps one state machine per CPU: the running thread, READY timestamps, the ISR stack and the open kernel call.
- Latencies go into 128 quarter-octave log buckets, giving p50, p99, p99.9 and max without storing samples.
- For each missed deadline, the last non-idle thread that ran on that CPU is recorded as the culprit.
- The timeline uses reservoir sampling (6,000 segments), so memory stays constant for any trace size.

Benchmark on a synthetic 150 MB, 2.24 M-event trace (laptop, Node 24): **1.9 s, 26 MB heap**.

## Status
The bundled sample (`sample/robot_trace.txt`, generated by `tools/gen_sample.mjs`) is **synthetic**: it is written in traceprinter's format but does not come from a real target. Validation against real SDP 8.0 + QEMU traces is in progress. Parser fixes will follow any format differences found there.
